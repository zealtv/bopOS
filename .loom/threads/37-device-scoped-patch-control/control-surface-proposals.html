Proposal 01 · priority — before presets (41)
Recommended shape

Per-parameter generator affordance

Let any numeric parameter run a generator (LFO / ramp / …) straight from the control surface, not only through the Show inspector’s message builder. The generator builder already exists — automation-2 compiles it to the OSC §3.2 wire grammar — so this is an extraction-and-placement problem, not a new mechanism.

Recommendation

Give every numeric control a two-state mode switch — value ▸ gen. Flipping to gen opens an inline drawer that hosts the extracted automation-2 builder; the value slider becomes a live preview of the generator’s output. One control, one param address, two authoring modes — the same component in the editor, the Device tab, and the Control tab.

decision

Drawer vs popover. Inline drawer (shown) keeps the param in place and reads well in the editor; a popover keeps rows dense on the All card where dozens of params stack. Recommendation: inline in editor/Device, popover on the All aggregate. Confirm or collapse to one.

open

Mixed aggregate. On the All / Group card, some seats may run a generator and others a static value on the same param. Does gen mode on an aggregate broadcast one generator to all, or is it disabled when members disagree? (Mirrors the existing mixed-value readout.)

open

Stop affordance. Where does “stop the generator, keep the last value” live — a third seg state, or a control inside the drawer?

Seam to 41. What a generator means inside a preset (captured spec vs captured value) stays the preset primitive’s design. This proposal only settles authoring a generator live; presets consume the same wire grammar later.
Proposal 02 · the Ciro Toast path
Recommended shape

Device-tab “Set patch…” hand-off

An operator working one node shouldn’t hunt for it inside a fleet picker. From a selected device on the Device tab, hand off to the target picker pre-scoped to that device — and resolve the wire reality that content ops target by seat.

Recommendation

Put a Set patch… button in the Device-tab patch-diagnostics panel. It routes to the Control-tab target picker with the target pre-selected to this device. For an unbound device it first offers a one-click “Give this device a seat” — because pinning needs a seat, and the operator shouldn’t have to learn why.

Proposal 03 · the shared component
Recommended shape

Per-device live-control placement & shape

Today the dashboard:true promoted controls render for All / Group / Seat. This defines one reusable control-surface component and its shape when hosted on the Device tab, scoped to a single device’s current patch.

Recommendation

Extract a single <ControlSurface scope patch> component — the param-tree renderer plus the value/gen row — and host it in three places with only its scope and patch differing: the patch editor, the Device tab (this device), and the Control tab (All/Group/Seat). On the Device tab it sits below diagnostics as a collapsible panel, which retires the Seats-detail vertical-overflow complaint rather than patching it.

Proposal 04 · information architecture
Recommended shape

Dashboard → Control tab rename

The tab where an operator drives the running installation is under-named. Rename it Control, give it a target filter (All / Groups / Seat), and settle where cues, master, and presets sit — with the cue section shrunk.

Recommendation

Rename the live-controls tab to Control. Put a target filter (All / Groups / Seat) at the top as a segmented control that scopes the shared surface below it. Keep cues + master as a compact strip above the surface; reserve a Presets shelf on the same tab (its contents are 41’s design).
